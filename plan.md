# MisFinanzas Family — Implementation Plan

> **Status:** Implemented (default recommendations). App lives in this repo; run `npm run dev`.  
> **Source app:** [finanzaslocales.lovable.app](https://finanzaslocales.lovable.app/) (“MisFinanzas Local Only”)  
> **Goal:** Clone the product with a **secure multi-user database**, **authentication**, and **household/family sharing** so several family members can use and contribute to the same finances.

---

## 1. Analysis of the current app

### 1.1 What it is

Spanish-language personal finance SPA branded **MisFinanzas**, dark UI, built with Lovable (React + Vite-style stack). Title explicitly says **“Local Only”**: all persistence is browser **localStorage**, no backend, no login.

### 1.2 Stack (inferred from production bundle)

| Layer | Technology |
|--------|------------|
| UI | React 18, React Router |
| Components | Radix UI + Tailwind (shadcn-style) |
| Icons | lucide-react |
| Dates | date-fns (`es` locale) |
| Toasts | sonner |
| Persistence | `localStorage` key `finance-app-data` |
| Export crypto | Web Crypto: **PBKDF2 + AES-GCM** → `.enc` files |
| PDF | pdf.js (Banamex statement MSI import) |
| Hosting | Lovable static deploy |

### 1.3 Navigation / screens (feature map)

| Route | Label | Purpose |
|-------|--------|---------|
| `/` | Dashboard | Month summary: ingresos / gastos / balance, account balances, top categories, credit cards, latest transactions |
| `/accounts` | Cuentas | Bank/cash accounts, balances, transfers between accounts |
| `/transactions` | Transacciones | CRUD incomes/expenses; filters; pagination |
| `/budgets` | Presupuestos | Per-category monthly (quincena-aware) budgets; copy budgets; spend vs budget |
| `/credit-cards` | Tarjetas | Cards with last-4, cut-off day, grace days; cycle spend; payment deadlines |
| `/recurring` | Recurrentes | Recurring incomes (day-of-month) + MSI installment plans |
| `/debts` | Deudas | Loans/debts: principal, APR, monthly payment, payment day; capital/interest payments history |
| `/safe-to-spend` | ¿Cuánto gastar? | Cash-flow projection: safe-to-spend, min balance, future incomes/expenses |
| `/import-statement` | Estado de cuenta | Import Banamex PDF; detect MSI installments; assign to cards |
| `/import-export` | Importar/Exportar | Full encrypted backup export/import (password-protected `.enc`) |
| `/settings` | Configuración | Categories CRUD; wipe all data |

**Catch-up assistant (“Ponerme al día”):** prompted from last visit (`finance-app-last-visit`). Bulk entry for missed expenses/incomes (auto-category by keyword), real-balance adjustments, debt payments while away.

### 1.4 Data model (localStorage blob)

Single JSON document under `finance-app-data`:

```
{
  transactions: [],
  categories: [],      // seeded defaults
  budgets: [],
  creditCards: [],
  accounts: [],        // seeded: Efectivo, Cuenta de cheques, Tarjeta de débito
  installmentPlans: [],
  recurringIncomes: [],
  debts: [],
  debtPayments: []
}
```

**Reducer actions (CRUD surface to reimplement as API):**

- Transactions: `ADD_TRANSACTION`, `ADD_TRANSACTIONS`, `UPDATE_TRANSACTION`, `DELETE_TRANSACTION`
- Categories / Budgets / Credit cards / Accounts: full ADD / UPDATE / DELETE
- Installment plans: ADD / DELETE (cascade deletes linked installment transactions)
- Recurring incomes: ADD / UPDATE / DELETE
- Debts + debt payments: ADD / UPDATE / DELETE (+ cascade payments on debt delete)
- `SET_DATA` (full replace — used by import)

**Default categories (seed):**

- Expense: Alimentación, Transporte, Vivienda, Entretenimiento, Salud, Educación, Ropa, Servicios, Otros gastos  
- Income: Salario, Freelance, Inversiones, Otros ingresos  

**Default accounts:** Efectivo (`cash`), Cuenta de cheques (`checking`), Tarjeta de débito (`debit`).

**Core entity fields (from runtime objects):**

| Entity | Key fields |
|--------|------------|
| Transaction | `id`, `date`, `amount`, `description`, `categoryId`, `type` (`income` \| `expense` \| `transfer`), `accountId?`, `toAccountId?`, `creditCardId?`, `installmentPlanId?`, `isAutoGenerated?` |
| Account | `id`, `name`, `type`, `icon`, `initialBalance` |
| Category | `id`, `name`, `type` (`income` \| `expense`), `icon`, `color` |
| Budget | `id`, `categoryId`, `amount`, `month` (period key) |
| Credit card | `id`, `name`, last 4, cut-off day, grace days, … |
| Installment plan (MSI) | `description`, `totalAmount`, `months`, `monthlyAmount`, `creditCardId`, `categoryId`, `startDate`, `createdAt` |
| Recurring income | `description`, `amount`, `categoryId`, `accountId`, `dayOfMonth`, `active` |
| Debt | name, principal, annual interest %, monthly payment, payment day, notes |
| Debt payment | `debtId`, `date`, `amount` (capital), `interestAmount`, `accountId`, `notes?` |

**UX details worth preserving:**

- Mexico-oriented: **MSI** (meses sin intereses), Banamex PDF import, Spanish copy, `$` + `es-MX`-style formatting  
- Auto-categorization from description keywords (merchant dictionary: Total Energies, Oxxo-style groceries, etc.)  
- Glass/dark dashboard cards  
- Month selector on dashboard  
- Balance = `initialBalance` ± transactions up to a date  

### 1.5 Security / multi-user limitations (why clone + DB)

| Issue | Impact |
|-------|--------|
| Data only in one browser’s localStorage | Lost on clear cache / new device; no sync across phones/PCs |
| No accounts | Anyone with device access sees all money data |
| No family model | Cannot share household budget safely with spouse/kids |
| Export is password-encrypted but optional | Primary store is plaintext JSON in localStorage |
| No audit trail | Cannot see who added a purchase |
| No roles | Teenagers cannot be limited to “add expense only” |
| Single blob `SET_DATA` | Race conditions if two tabs edit; worse with multi-user |

## 2. Product goals for the clone

1. **Feature parity** with MisFinanzas Local Only (all screens and flows above).  
2. **Secure database** as system of record (not localStorage).  
3. **Authentication** (email/password at minimum; optional OAuth later).  
4. **Household / family workspace**: multiple members share the same finances.  
5. **Roles & permissions** so not everyone has equal power.  
6. **Foundation** for future multi-member features (shared wishlists, allowances, notifications, etc.).  
7. Spanish-first UI (same product language as the original).

### 2.1 Non-goals (v1 unless you change this plan)

- Bank open-banking / automatic bank sync (Plaid, Belvo, etc.)  
- Mobile native apps (responsive web is enough)  
- Multi-currency / multi-country tax modules  
- Public multi-tenant SaaS marketing site  
- Real-time collaborative cursors

Prioritized for a **family** product. Mark items you want in v1 vs later.

### 3.1 Must-have for multi-member (v1)

| # | Change | Why |
|---|--------|-----|
| M1 | **Household** entity + invite flow (email or invite link) | Shared ledger instead of one person’s browser |
| M2 | **Login / logout / session** | Gate all financial data |

### 3.2 Strongly recommended (v1 or v1.1)

| R4 | **Soft-delete + recycle** instead of hard wipe | Accidents in shared data are costly |

| R6 | **Rate limiting + brute-force protection** on auth | Secure DB is useless if auth is weak |

## 4. Recommended architecture

### 4.1 High-level

```
┌─────────────────────┐     HTTPS + session      ┌──────────────────────────┐
│  React SPA (Vite)   │ ◄──────────────────────► │  API (Next.js or Fastify)│
│  Spanish UI clone   │      JWT / cookie        │  Auth + business rules   │
└─────────────────────┘                          └────────────┬─────────────┘
                                                              │
                                                              ▼
                                                 ┌──────────────────────────┐
                                                 │  PostgreSQL (managed)    │
                                                 │  + encrypted at rest     │
                                                 │  + backups / PITR        │
                                                 │  + RLS (if Supabase)     │
                                                 └──────────────────────────┘
```

### 4.2 Tech stack options (pick one — default recommended)

#### Option A — **Recommended default: Next.js + Supabase**

| Piece | Choice | Rationale |
|-------|--------|-----------|
| Frontend + API | Next.js 15 (App Router) | One deployable unit; server actions or route handlers |
| DB | **Supabase Postgres** | Managed Postgres, encrypted at rest, daily backups, connection pooling |
| Auth | **Supabase Auth** | Email/password, magic link, later Google/Apple; JWT + RLS |
| Authorization | **Row Level Security** on all tables | Defense in depth even if API bugs |
| Storage (later) | Supabase Storage | Receipts with signed URLs |
| Hosting | Vercel + Supabase | Simple ops for family app |

**Why this is the secure default for a family finance app:** Postgres + RLS means even a compromised client cannot read another household’s rows if policies are correct. Auth is not reinvented.

#### Option B — Custom backend

- Frontend: Vite + React (closer clone of Lovable output)  
- API: Node (Fastify/Nest) or Java (Spring)  
- DB: managed Postgres (Neon, RDS, Cloud SQL)  
- Auth: Better Auth / Lucia / Auth.js  

More control, more security work you own (session store, CSRF, password hashing, invite tokens).

#### Option C — Firebase

Possible but weaker fit for relational money data and complex RLS-style household rules. **Not recommended** for this domain.

> **Decision for you:** Confirm **Option A** or write your preferred stack in §11 before implementation.

### 4.3 Security requirements (non-negotiable)

1. **No localStorage for financial records** (session tokens may use httpOnly cookies only).  
2. **Password hashing** via Auth provider (bcrypt/argon2 — never custom).  
3. **All queries scoped by `household_id`** derived from session, never from client-supplied tenant alone.  
4. **RLS policies** (or equivalent server checks) for every table.  
5. **TLS everywhere**; HSTS in production.  
6. **Secrets** only in env / secret manager (DB URL, JWT secret, service role key never in browser).  
7. **Service role key** only on server; browser uses anon key + user JWT.  
8. **Input validation** (Zod) on every mutation; amounts as integer **cents** to avoid float bugs.  
9. **Audit log** table for destructive actions (delete account, wipe, role change).  
10. **Backups** enabled on the managed DB; document restore procedure.  
11. **Optional field-level encryption** for highly sensitive notes later (app-level); v1 relies on DB encryption at rest + access control.  
12. **CORS** locked to app origin; rate limit auth and invite endpoints.

### 4.4 Auth & household model

```
User ──< Membership >── Household
  │                         │
  │                         ├── Accounts, Categories, Budgets, …
  │                         └── Transactions (created_by → User)
  └── session / credentials
```

**Roles:**

| Role | Capabilities |
|------|----------------|
| `owner` | Full control; transfer ownership; delete household |
| `admin` | Manage members (except owner), categories, all CRUD on money data |
| `member` | Create/edit own transactions; view household data; limited settings |
| `viewer` | Read-only |

**Invite flow:**

1. Owner/admin creates invite (email + role, expires in N days).  
2. Invitee signs up / logs in and accepts → `membership` row.  
3. Optional: first user creates household during onboarding.

## 5. Target data model (Postgres)

> Amounts stored as **integer cents** (`amount_cents`). Dates as `date` / `timestamptz`. UUIDs for ids.

### 5.1 Identity & tenancy

```sql
-- users: managed largely by Supabase auth.users; profile extension:
profiles (
  id uuid PK references auth.users,
  display_name text,
  avatar_url text,
  locale text default 'es',
  created_at, updated_at
)

households (
  id uuid PK,
  name text not null,              -- e.g. "Familia García"
  currency text default 'MXN',
  created_by uuid references profiles,
  created_at, updated_at
)

memberships (
  id uuid PK,
  household_id uuid not null references households,
  user_id uuid not null references profiles,
  role text not null check (role in ('owner','admin','member','viewer')),
  unique (household_id, user_id)
)

invites (
  id uuid PK,
  household_id uuid not null,
  email text not null,
  role text not null,
  token_hash text not null,
  expires_at timestamptz not null,
  accepted_at timestamptz,
  created_by uuid
)
```

### 5.2 Finance tables (all include `household_id`)

Mirror the original domain, multi-tenant:

- `accounts`  
- `categories`  
- `transactions` (+ `created_by`, `spent_by` nullable, soft `deleted_at`)  
- `budgets`  
- `credit_cards`  
- `installment_plans`  
- `recurring_incomes`  
- `debts`  
- `debt_payments`  
- `activity_events` (optional v1.1)  
- `user_preferences` (last_visit per user for catch-up)

**RLS sketch (every finance table):**

```sql
-- user can only see rows for households they belong to
using (
  household_id in (
    select household_id from memberships where user_id = auth.uid()
  )
)
-- writes further restricted by role via policies or security definer functions
```

### 5.3 Migration from localStorage (optional tool)

Settings page: “Importar respaldo MisFinanzas (.enc o JSON)” → decrypt client-side if `.enc` → POST validated payload → map into household tables. One-time wizard with preview.

## 9. Testing strategy

| Layer | What |
|-------|------|
| Unit | Money arithmetic, period keys, safe-to-spend projection, auto-categorize |
| Integration | API + DB: RLS (user A cannot read household B), role denied writes |
| E2E (Playwright) | Login → invite → second user adds expense → dashboard updates |
| Security smoke | Unauthenticated 401; forged household_id ignored |

**Critical security tests:**

1. Cross-tenant isolation (mandatory).  
2. Viewer cannot POST transactions.  
3. Member cannot change roles.  
4. Export requires auth + role.  
5. Invite token single-use / expired rejected.

## 10. Risks & mitigations

| Risk | Mitigation |
|------|------------|
| RLS misconfiguration leaks data | Integration tests + least-privilege anon key; never ship service role to client |
| Float money bugs | Integer cents everywhere |
| Concurrent edits | Row updates with `updated_at`; avoid whole-blob `SET_DATA` |
| Banamex PDF layout changes | Isolate parser; fail gracefully with manual MSI entry |
| Family disputes over “who spent” | `spent_by` + activity feed |
| Lost owner account | Recovery email + optional second owner promotion |
| Scope creep | Ship Phase 1–2 first; family extras after parity |
